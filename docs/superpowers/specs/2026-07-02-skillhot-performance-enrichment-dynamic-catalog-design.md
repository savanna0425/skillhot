# SkillHot 性能、AI 解读与动态收录优化设计

日期：2026-07-02

## 背景

SkillHot 当前已经不是用户访问首页时实时请求 GitHub，而是通过 GitHub Actions 定时生成 `public/data/skills.json`，前端读取静态数据展示。用户反馈“首页慢”“希望做缓存”“每个项目能不能有 AI 说明”“为什么一直是 1502 个项目”后，可以看出产品需要从“GitHub skills 聚合榜单”升级为“打开快、解释清楚、动态收录规则透明的 AI 工具导航站”。

本次设计合并三类优化：

1. 首页和列表加载速度优化。
2. 每个项目增加离线生成的 AI 用途解读。
3. 将固定数量截断改为动态质量门槛，让收录数量自然浮动。

## 目标

- 首页首屏更快出现，不再依赖一次性加载完整仓库大 JSON。
- 用户能快速看懂每个项目的用途、适合场景和预期效果。
- 收录数量不再被 `1500` 这种固定展示上限决定，而是由质量规则决定。
- 前台文案能解释 SkillHot 是每日动态筛选更新，不是固定仓库池。
- 后台仍然控制 GitHub API、README 抓取和 AI 生成预算，避免成本失控。

## 非目标

- 不做用户访问时实时调用 GitHub API。
- 不做用户访问时实时调用大模型生成项目解读。
- 不在第一版引入复杂后台管理系统。
- 不把所有 GitHub 搜索结果无差别收录。
- 不承诺每个项目的 AI 解读都达到人工评测质量，第一版以可用、可校验、可增量改进为主。

## 产品定义

SkillHot 的定位调整为：

> 每日动态筛选的 Agent Skills 与 AI 工具技能导航站。

前台推荐文案：

- “当前动态收录 X 个项目”
- “每日从 GitHub 自动筛选更新”
- “今日新增 X 个，更新 X 个，移出 X 个”
- “AI 帮你快速理解项目用途、适合场景和预期效果”

## 数据加载设计

### 当前问题

当前首页通过 `src/App.tsx` 一次性请求 `data/skills.json`。这个文件包含完整项目列表、分类、话题和详情字段。随着项目数量增长，首页首屏会受数据包大小、JSON 解析、图片加载和卡片渲染影响。

### 目标结构

将单一数据文件拆分为多层静态文件：

```text
public/data/
  manifest.json
  home.json
  skills-lite.json
  categories.json
  topics.json
  categories/
    编程开发.json
    Agent工具与平台.json
  topics/
    claude-skills.json
    agent-skills.json
  details/
    obra__superpowers.json
    farion1231__cc-switch.json
```

### 文件职责

`manifest.json`

- 当前数据版本。
- 生成时间。
- 动态收录总数。
- 今日新增、移出、更新数量。
- 各数据文件路径。

`home.json`

- 首页首屏所需的轻量数据。
- 包含热门榜单、最新收录、上升项目、核心统计。
- 不包含全部详情。

`skills-lite.json`

- 全量轻量索引。
- 用于搜索、榜单和基本列表展示。
- 字段只保留列表必要信息：名称、简介、分类、星数、活跃度、标签、图片 URL、AI 一句话用途。

`details/*.json`

- 单个项目详情。
- 用户打开详情面板时按需加载。
- 包含 README 提取信息、AI 解读、安装方式、使用场景、注意事项等。

`categories/*.json` 和 `topics/*.json`

- 分类页和话题页按需加载。
- 继续保留“加载更多”分页体验。

### 前端加载流程

1. App 启动时优先加载 `manifest.json` 和 `home.json`。
2. 首页立即渲染轻量首屏。
3. 用户进入榜单、搜索、分类或话题时再加载对应数据。
4. 用户打开项目详情时再加载详情 JSON。
5. 对已经加载过的数据做浏览器内存缓存，避免重复请求。

## 缓存策略

### 静态缓存

- `index.html`：短缓存，保证新版本能及时生效。
- JS/CSS 资源：继续使用 Vite hash 文件名，长缓存。
- 数据文件：建议使用 `manifest` 版本号和内容 hash。

第一版可以保持固定路径，依赖 GitHub Pages 的缓存策略和 query version。第二版再升级为 hash 数据文件名。

### 更新方式

继续使用 GitHub Actions 定时更新，不在用户访问时更新。

更新频率建议：

- 每天北京时间 08:20 执行常规数据更新。
- 必要时允许手动触发 workflow。
- AI 解读增量生成可以放在同一 workflow 或单独 workflow 中。

## 动态收录规则

### 当前问题

当前脚本中有固定上限：

```js
const maxRepositories = 1500
```

脚本会从候选池打分排序后截取前 1500，再额外补充精选仓库，所以当前数量稳定在 1502。这会让用户以为仓库池是固定的。

### 新规则

移除“固定展示上限”的产品含义，改成“动态质量门槛”。

项目进入 SkillHot，需要满足基础条件：

- 公开可访问。
- 非 fork。
- 非 archived。
- 与 Agent Skills、Claude Skills、Codex Skills、AI 工具技能生态相关。
- 相关性评分达到收录阈值。

并满足以下任一加强条件：

- 精准 topic 命中，例如 `agent-skills`、`claude-skills`、`codex-skills`。
- README 明确包含 Skill 使用结构、`SKILL.md`、Claude Skill、Agent Skill 等信息。
- stars 达到阈值，并且最近一年有更新。
- 被人工精选。
- 属于官方、生态核心、合集、注册表、marketplace 或高价值工具。

### 排除规则

自动排除：

- archived 仓库。
- fork 仓库。
- 删除或 404 仓库。
- 明显无关项目，例如游戏技能、普通英语学习技能、个人简历技能。
- README 和 description 都过弱，且星数、活跃度、相关性不足。
- 长期无人维护且价值信号不足的项目。

### 评分模型

建议总分由以下部分组成：

```text
总分 = 相关性分 + 星数分 + 活跃度分 + 生态价值分 + 内容完整度分 + 人工精选加分 - 风险扣分
```

字段解释：

- 相关性分：是否真正属于 Agent Skills / Claude Skills / Codex Skills 生态。
- 星数分：项目受欢迎程度，做平滑处理，避免高星但无关项目霸榜。
- 活跃度分：最近 30 / 90 / 365 天是否更新。
- 生态价值分：官方仓库、合集、registry、工具平台、教程等加分。
- 内容完整度分：README、安装方式、示例、文档是否完整。
- 人工精选加分：保证核心项目不会因为搜索排名波动被移出。
- 风险扣分：无 README、疑似无关、长期不活跃、描述弱等。

### 状态机制

每个项目增加收录状态：

- `new`：今日新收录。
- `active`：正常收录。
- `watching`：观察中，暂不移除。
- `hidden`：不再前台展示。

退出规则：

- archived、删除、404：立即隐藏。
- 明显无关：立即隐藏。
- 低分项目：进入观察期，连续多次低于阈值后隐藏。

这样前台数量会自然浮动，例如今天 1538，明天 1544，后天 1536。

## 每日 diff 设计

为了解释“动态更新”，数据管道需要保存上一版快照，并生成 diff：

```json
{
  "added": ["owner/repo"],
  "removed": ["owner/repo"],
  "updated": ["owner/repo"],
  "rankUp": ["owner/repo"],
  "rankDown": ["owner/repo"]
}
```

前台可展示：

- 今日新增。
- 最近更新。
- 排名上升。
- 本周活跃。
- 已不再展示数量。

第一版只需要 `added`、`removed`、`updated` 三类即可。

## AI 项目解读设计

### 用户价值

用户点开一个项目时，不应该只看到 GitHub 描述，而应该快速理解：

- 这个项目是做什么的？
- 适合谁用？
- 能解决什么问题？
- 用了之后有什么效果？
- 怎么开始用？
- 有什么注意事项？

### 字段设计

每个项目详情增加：

```json
{
  "aiSummary": "一句话解释项目用途",
  "useCases": ["适合场景 A", "适合场景 B"],
  "expectedEffects": ["能带来的效果 A", "能带来的效果 B"],
  "targetUsers": ["开发者", "产品经理"],
  "gettingStarted": "最短上手方式",
  "limitations": ["需要 API Key", "文档较少"],
  "aiGeneratedAt": "2026-07-02T00:00:00.000Z",
  "aiSourceHash": "readme-and-metadata-hash"
}
```

### 生成方式

AI 解读必须离线生成：

1. 数据更新脚本收集 GitHub metadata 和 README。
2. 计算项目输入 hash。
3. 如果项目是新增，或 hash 变化明显，则进入 AI 解读队列。
4. 按每日预算处理队列。
5. 生成结果写入静态 JSON。
6. 前端只读取生成好的内容，不实时调用模型。

### 成本控制

第一版建议：

- 只处理新增项目。
- 优先处理 Top 100 / Top 300。
- 已生成且 hash 未变化的项目直接复用。
- 每天限制 AI 生成数量，例如 30 到 100 个。
- 失败项目进入下次重试，不阻塞整个数据更新。

### 质量控制

生成提示词应要求：

- 不夸大项目能力。
- 不编造不存在的功能。
- 明确说明“根据 README 和 GitHub 元数据总结”。
- 如果信息不足，要输出“信息较少，建议查看 README”。
- 避免营销腔。

第一版可以不做人工审核，但保留 `aiConfidence` 或 `limitations` 字段，方便前台谨慎展示。

## 前端展示设计

### 首页

首页首屏展示：

- 当前动态收录数量。
- 今日新增 / 更新 / 移出。
- 热门项目。
- 新收录项目。
- 本周活跃项目。

首页不加载全部详情。

### 列表卡片

卡片展示轻量 AI 一句话用途，例如：

> 用来管理 Claude Code / Codex 等编程智能体配置的工具。

### 详情面板

详情面板增加“AI 解读”区域：

- 这个项目做什么。
- 适合谁。
- 典型场景。
- 预期效果。
- 上手方式。
- 注意事项。

如果项目没有 AI 解读，则回退到当前 summary、description 和 README 入口。

### 动态标签

卡片可增加：

- 新收录
- 本周活跃
- 排名上升
- AI 已解读
- 精选来源

## 数据管道改造

### 阶段一：轻量拆包

- 继续生成完整 `skills.json` 作为兼容文件。
- 新增 `manifest.json`、`home.json`、`skills-lite.json`。
- 前端先切首页到 `home.json`。
- 保持旧页面可回退到 `skills.json`。

### 阶段二：动态收录

- 移除前台意义上的固定 `maxRepositories`。
- 增加收录阈值。
- 增加上一版快照对比。
- 生成每日 diff。
- 前台显示动态更新状态。

工程上可以保留 GitHub API 抓取预算，例如搜索页数、README 读取数量、AI 生成数量。这个预算不是前台展示数量上限。

### 阶段三：AI 解读

- 新增离线 enrichment 脚本。
- 新增 AI 解读缓存文件。
- 先处理新增项目和高排名项目。
- 前端详情面板展示 AI 解读。

## 错误处理

- `manifest.json` 加载失败：显示错误状态，提供重试。
- `home.json` 加载失败：回退加载旧 `skills.json`。
- 分类/话题数据加载失败：显示局部错误，不影响整个页面。
- 详情 JSON 加载失败：回退当前已有详情字段。
- AI 解读缺失：隐藏 AI 区域或显示基础摘要。
- GitHub API 额度不足：使用上一版数据，workflow 标记为部分更新。
- AI 生成失败：跳过该项目，记录失败原因，不阻塞发布。

## 测试计划

### 数据测试

- 校验 `manifest.repositories` 与实际收录数量一致。
- 校验 `home.json` 中项目都能在 lite/detail 数据中找到。
- 校验新增、移出、更新 diff 格式正确。
- 校验分类和话题文件不存在空列表异常。
- 校验 AI 解读字段长度、数组数量和必要字段。

### 前端测试

- 首页只依赖 `manifest.json` 和 `home.json` 即可渲染首屏。
- 分类页、话题页仍可加载更多。
- 搜索和榜单能按需加载轻量索引。
- 打开详情时能按需加载详情 JSON。
- AI 解读缺失时页面不报错。

### 性能验证

- 对比优化前后的首页首屏请求大小。
- 对比首页可交互时间。
- 确认图片懒加载生效。
- 确认控制台无相关 error / warn。

## 实施顺序

推荐按三步做，不一次性上大改：

1. 首页轻量数据与分包加载。
2. 动态收录规则与每日 diff。
3. AI 项目解读离线生成与详情展示。

原因：

- 性能是用户第一感知，应先解决。
- 动态收录规则影响数据口径，应在 AI 解读前稳定。
- AI 解读有成本和质量问题，适合最后增量接入。

## 开放问题

1. 第一版是否继续保留完整 `skills.json` 兼容旧逻辑？
   - 建议保留，降低回滚风险。
2. 动态收录阈值初始值设多少？
   - 建议先用当前打分分布反推，避免一次性移除太多项目。
3. AI 解读使用哪个模型和预算？
   - 建议先用低成本模型离线处理新增和 Top 300。
4. 前台是否展示“移出项目”？
   - 建议第一版只展示新增和更新，移出放在统计里，不做单独列表。
5. 是否需要人工审核 AI 解读？
   - 建议第一版不强制人工审核，但保留人工 override 能力。

## 验收标准

- 首页不再依赖完整 `skills.json` 即可完成首屏渲染。
- 首页展示动态收录文案和今日更新统计。
- 收录数量可自然浮动，不再由固定 `1500` 上限决定。
- 分类页、话题页、榜单页仍可完整浏览项目。
- 至少热门项目或新增项目能展示 AI 用途解读。
- 数据更新失败时网站仍可展示上一版可用数据。
- 本地 `pnpm check`、`pnpm build`、`pnpm test:e2e` 通过。
